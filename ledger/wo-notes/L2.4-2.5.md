## 2. L2.4 — อัลกอริทึมและค่าคงที่

### 2.1 กติกา
1. **ฐาน HR ตอนตื่น** = ค่าเฉลี่ย `hrMean` ของ epoch ที่มีข้อมูล 10 ตัวแรก (5 นาทีแรก)
2. **หน้าต่างเงียบ** = 20 epoch ล่าสุด (10 นาที) ต้องผ่านทุกข้อ
   - ค่าเฉลี่ย motion ≤ `motionQuiet × 2` = 0.04 g
   - epoch ที่เกิน 0.02 g (ขยับสั้น/พลิกตัว) ≤ 4 ตัว
   - ไม่มี epoch ไหนเกิน 0.25 g (นั่นคือ "ตื่นอยู่" ไม่ใช่กระตุก)
   - มีข้อมูล motion จริง ≥ 60% ของหน้าต่าง (ทนนาฬิกาหลุดเป็นช่วง)
3. **เส้นทางประกาศ onset** สองทาง
   - `SETTLED` (ทางหลัก): หน้าต่างเงียบครบ 10 นาที **และ** HR เฉลี่ยในหน้าต่าง ≤ ฐาน (หัวใจเลิกสูงกว่าตอนตื่นแล้ว)
   - `DEEP` (ทางยืนยัน): HR เฉลี่ย ≤ ฐาน×(1−0.08) ตามตัวอักษรของ §5.1 — ใช้หน้าต่างครึ่งเดียว (5 นาที) ก็ประกาศได้
   - `TIMER`: ข้อมูลใช้ได้ ≤ 50% ของ epoch ที่ผ่านมา (รวมกรณีไม่มีเซนเซอร์เลย) → onset = `start + 1500`
4. **ห้ามประกาศก่อนมีข้อมูล 15 นาที** (`minDataSec` 900) — ประกาศเร็ว = GUARD เริ่มเร็ว = อันตรายกว่าเสมอ
5. `onsetT` = **เวลาของ epoch แรกของหน้าต่างเงียบ** แต่ไม่เร็วกว่า `start + 900` (`minLatencySec`)

### 2.2 ทำไมต้องมีทาง `SETTLED` (ไม่ใช้ −8% ตรง ๆ)
`wo-notes/L2.1.md` §8 เตือนไว้แล้ว และผมวัดซ้ำแล้วจริง: ฐาน 5 นาทีแรกอยู่ใน N1/N2 อยู่แล้ว (N1 = +2 bpm, N2 = ±0 จากฐานคืนนั้น) ⇒ เกณฑ์ −8% จะไปถึงก็ต่อเมื่อเข้า **N3** ซึ่งอยู่ราว 26 นาทีหลัง onset จริง (N2a ของรอบแรก ≈ 53 epoch)

**หลักฐาน** (สคริปต์วัดอยู่ใน `.heavy/` ซึ่ง gitignore — สูตรเขียนไว้ตรงนี้ครบแล้ว · 200 คืน): ถ้าใช้กติกา §5.1 ตามตัวอักษร (หน้าต่าง 10 นาทีเงียบ **และ** HR เฉลี่ย ≤ ฐาน×0.92) มันยิงทุกคืนจริง แต่ช้ากว่าเฉลย **มัธยฐาน 1,440 วิ (24 นาที)** · p10 1,200 วิ · p90 1,680 วิ ⇒ **เข้ากรอบ ±10 นาที 0 คืนจาก 200** · ทาง `SETTLED` จึงเป็นทางหลัก และเก็บ −8% ไว้เป็นทางยืนยัน (ในเวอร์ชันแรกที่เกณฑ์ motion เข้มกว่านี้ ทาง `DEEP` ช่วยไว้ 6 คืน · เวอร์ชันสุดท้ายประกาศด้วย `SETTLED` ทั้ง 200 คืน)

### 2.3 ทำไม `onsetT` ถึงมีพื้น 15 นาที (ข้อสำคัญที่สุดของใบนี้)
ในตัวจำลอง (และในสรีรวิทยา) ช่วง latency หลัง N1 คือ **N2** และช่วงหลัง onset ก็คือ **N2** เหมือนกันเป๊ะ — HR เท่ากัน ขยับเท่ากัน hrSd เท่ากัน ⇒ **ข้อมือมองไม่เห็นรอยต่อ N1→N2 เลย** สิ่งที่ตัวจับทำได้จริงคือ "ยืนยันว่าหลับแล้ว" ไม่ใช่ "บอกว่าหลับตอนไหน"
- prior ของ latency = 5–25 นาที (uniform) ⇒ ค่าที่ทำให้ error สูงสุดต่ำสุดคือ **15 นาที** (พิสูจน์ด้วยการกวาด: พื้น 780/840/900/960 วิ → ผ่าน 96.5% / 98.5% / **99.5%** / 96.0%)
- ผลคือ onset ที่รายงาน **มาจาก prior เป็นหลัก ไม่ใช่จากหลักฐาน** และตัวเลข 99.5% ข้างล่างจึง "ดีเกินจริง" เพราะข้อสอบให้กรอบ ±10 นาทีซึ่งกว้างพอ ๆ กับ prior เอง → ดู §6 หนี้ข้อ 1

### 2.4 ค่าคงที่ (export ทุกตัว แก้ผ่าน `OnsetOptions` ได้)
```
noSensorTimeoutSec 1500 · baselineEpochs 10 · quietEpochs 20 (=10 นาที)
hrDropRatio 0.08 · motionQuiet 0.02 g · motionMove 0.25 g · maxTwitchEpochs 4
motionMeanFactor 2 (ค่าเฉลี่ยในหน้าต่าง ≤ 0.04) · minCoverage 0.6 · timerCoverage 0.5
minDataSec 900 · minLatencySec 900 · bed 0.20→0.08 ใน 60 วิ · seed +180/+480 · guard ขั้นต่ำ 2 ชม.
```
ที่มาของ `maxTwitchEpochs`/`motionMeanFactor`: ในตัวจำลอง N2 มีโอกาสกระตุก 8% ต่อ epoch ⇒ หน้าต่าง 20 epoch "เงียบสนิททุกตัว" มีโอกาสแค่ `0.92²⁰ ≈ 19%` ถ้าใช้ตัวอักษร "ทุก epoch ≤ 0.02" ตามใบสั่งงาน ตัวจับจะรอเฉลี่ยนาน ~26 นาทีหลังเข้า N2 และ error กระจายแบบ exponential — จึงเปลี่ยนเป็น "ค่าเฉลี่ยต่ำ + กระตุกได้ไม่เกิน 4 ตัว + ห้ามมี epoch ขนาดตื่น" (แจ้งเป็นข้อแย้ง §7.1)

## 3. L2.5 — อัลกอริทึมและค่าคงที่

### 3.1 สมการ
```
p = sigmoid( bias + 1.0·prior + 1.2·hrRel + 1.2·hrSdRel + 0.8·motionLow + 0.6·hist + 2.5·eog )
```
น้ำหนักตรงตาราง §5.2 ทุกตัว (`eog` = ช่องหลักฐานที่ 5 ในอนาคต · ฟีเจอร์ = 0 จนกว่าจะมีหน้ากาก EOG ⇒ ไม่มีผลใด ๆ วันนี้)

**หลักการออกแบบฟีเจอร์: เครื่องหมายอยู่ที่ฟีเจอร์ ความแรงอยู่ที่น้ำหนัก** ทุกฟีเจอร์เป็นค่าบวก/ลบรอบศูนย์ และ "ไม่มีสัญญาณ = 0" พอดี ⇒ น้ำหนักทุกตัว (รวม bias) clamp `[0,5]` ได้ตามข้อสอบ Q6 โดยที่โมเดลยังทำนาย "ไม่ใช่ REM" ได้ (ค่าลบมาจาก prior + โทษการขยับ)

| ฟีเจอร์ | สูตร | ค่ามัธยฐานที่วัดได้จริง (30 คืน · REM / N2 / N3 / WAKE) |
|---|---|---|
| `prior` | log-odds ของ REM จากเวลา — ดู §3.2 | −1.07 / −1.33 / −1.69 / −1.10 (ช่วงทั้งหมด −3.2 … −0.92) |
| `hrRel` | (ค่าเฉลี่ย HR 5 นาที − median คืนนี้) / (IQR/1.349 · clamp 1.2–8) · clamp [−3, **1.0**] | **+0.94** / −0.01 / −1.15 / +1.00 (WAKE ถูกตัดที่เพดาน) |
| `hrSdRel` | (ค่าเฉลี่ย hrSd 3 epoch − median คืนนี้) / max(0.5, median) · clamp [−2, 3] | **+1.55** / +0.02 / −0.45 / +1.93 |
| `motionLow` | ดูหน้าต่าง 2 นาทีล่าสุด: เฉลี่ย ≤ 0.02 → **+0.5** · มี epoch > 0.15 g หรือมี ≥ 2 epoch > 0.06 g → **−5** · นอกนั้น 0 | +0.5 / +0.5 / +0.5 / **−5** (โดน −5: REM 0.2% · N2 2.7% · WAKE 99.9%) |
| `hist` | `log((h+ε)/(mean+ε))` ของช่อง 30 นาที (UTC) · clamp ±2 · ไม่มีฮิสโตแกรม = 0 | 0 จนกว่า L2.9 จะป้อน |

อ่านตารางนี้ให้ออกคือเข้าใจโมเดลทั้งตัว: **`hrSdRel` คือคนที่แบกงาน** (REM +1.55 vs N2 +0.02 แทบไม่ทับกัน) · `hrRel` ช่วยแยก N3 ออก · `motionLow` มีหน้าที่เดียวคือตัด WAKE ทิ้ง (ซึ่ง hrSd ของมันหน้าตาเหมือน REM เป๊ะ) · `prior` กดทั้งชั่วโมงแรกและตั้งระดับฐาน

median/IQR เป็น **running ของคืนนี้เท่านั้น (causal)** ⇒ สตรีม = batch เป๊ะ (Q5 ต่าง 0.0)

### 3.2 รูปของ prior (DESIGN §5.2 "ต่ำมาก < 60 นาที · สูงขึ้นทุกรอบ · สูงสุดครึ่งหลัง")
```
m = นาทีตั้งแต่ onset
m < 60            → priorCold = −3.2                       (REM latency ≥ 60 นาทีในคนปกติ)
60 ≤ m < 70       → ไล่เชิงเส้นจาก −3.2 เข้าเส้นอุ่น        (กัน p กระโดดใน 1 epoch)
m ≥ 70            → −1.9 + 0.55/(1+0.35·(รอบที่−1))·bump(phase) + 0.75·frac
bump = 0.5(1+cos(2π(phase−0.92)))   phase = (m mod 90)/90  ⇒ ยอดที่ท้ายรอบ 90 นาที
frac = สัดส่วนของคืนที่ผ่านไป (onset → expectedEndT)
```
ยอดสูงสุดของ prior ที่เป็นไปได้ = **−0.923** ⇒ ถ้าไม่มีเซนเซอร์เลย p สูงสุด = **0.338** (Q4 ต้อง ≤ 0.75) — ตัวเลขนี้มีผลกับ §5.1 "โหมดไม่มีนาฬิกา" ดูข้อแย้ง §7.2

### 3.3 `updateWeights` — ทำไมถึงขี้ขลาดขนาดนี้
1. gradient แบบ **ค่าเฉลี่ยทั้งคืน** (ไม่ใช่ SGD ราย epoch) 2 รอบ · lr 0.02
2. น้ำหนักตัวหนึ่งขยับได้ไม่เกิน **0.05 ต่อคืน** · clamp `[0,5]` รวม bias
3. **ด่านกัน F1 ตก**: คำนวณ F1 ที่ threshold 0.70 ของคืนที่เพิ่งเรียน ก่อน/หลังอัปเดต ถ้าหลังต่ำกว่าก่อนเกิน 0.002 → **ทิ้งอัปเดตทั้งก้อน**
4. คืนน้ำหนักเดิมทันทีเมื่อ: ไม่ได้ส่ง `epochs` มา · ไม่มี `pRemSamples` · คืนนั้นไม่มี REM ในเฉลย
5. deterministic เต็มตัว (ไม่มีสุ่ม ไม่มี shuffle ไม่อ่านนาฬิกา)

**ข้อ 3 ไม่ใช่การประดับ — มันกันระเบิดจริง**: gradient ลด log-loss แต่แอปตัดสินที่ *เกณฑ์* 0.70 สองอย่างนี้ไม่ใช่เรื่องเดียวกัน วัดได้ว่าเริ่มจากน้ำหนักแย่ ๆ แล้วอัปเดต 60 คืนติด **log-loss ดีขึ้น 0.78 → 0.31 แต่ F1 ร่วง 0.86 → 0.15** (โมเดลบีบ p ทุกตัวลงใต้ 0.70 ⇒ คืนนั้นเงียบสนิท ไม่มี cue) พอใส่ด่านแล้วเคสเดียวกันได้ F1 **0.937**

## 6. หนี้ / ข้อจำกัด (แผนปรับเทียบที่ R2)

1. **onset ที่รายงานมาจาก prior เป็นหลัก** — ข้อมือไม่มีสัญญาณแยก "N2 ก่อนหลับ" กับ "N2 หลังหลับ" (§2.3) ตัวเลข 99.5% ได้มาเพราะกรอบ ±10 นาทีกว้างพอ ๆ กับ prior 5–25 นาที **ห้ามอ้างว่าตัวจับหลับ "แม่น 99.5%"** กับผู้ใช้หรือในหน้าสถิติ
   *แผน R2*: เก็บ 10–14 คืนจริงพร้อมสเตจ Apple → เทียบ `onsetT` ของเรากับ `asleepCore` ตัวแรกของ Apple → ปรับ `minLatencySec` ให้เป็น **median latency ของเจ้าของ** (ไม่ใช่ 15 นาทีของประชากร) และเปลี่ยน prior เป็นรายบุคคลได้ทันทีเพราะเป็น option อยู่แล้ว
2. **F1 0.98 บนคืนจำลอง = ดีเกินจริงแน่นอน** — ต่อยอดจาก `wo-notes/L2.1.md` หนี้ข้อ 2: ช่องว่าง `hrSd` REM(4–6) vs N3(~1) ในตัวจำลองกว้างกว่าที่นาฬิกาจริงวัดได้ (นาฬิกามี noise การวัดบวกมาอีก) และ `hrSdRel` คือฟีเจอร์ที่แบกงานเกือบทั้งหมดของโมเดลนี้ **ถ้าของจริงช่องว่างแคบลงครึ่งหนึ่ง F1 จะร่วงแรง** ตัวเลขที่ควรคาดหวังจากงานวิจัยนาฬิกาข้อมือคือ F1 ราว 0.5–0.7 ไม่ใช่ 0.98
   *แผน R2*: (ก) เก็บคืนจริง + สเตจ Apple ผ่าน L2.9 → (ข) วัด `hrSd` ต่อสเตจจริง แล้วแก้ `HR_SD`/`HR_JITTER` ใน `simulate.ts` ให้ตรง → (ค) รัน Q1 ใหม่และ **ลดเกณฑ์ข้อสอบตามจริง** (APP-RUN เขียนไว้แล้วว่า "เกณฑ์ตั้งต้น ปรับตามคืนจริง R2") → (ง) fit `DEFAULT_REM_TUNING` ใหม่ทั้งชุด (ทุกค่าเป็น option อยู่แล้ว ไม่ต้องแก้โค้ด)
3. **ค่าคงที่ถูก fit บนตัวจำลองเดียวกับที่ใช้วัด** — ไม่มี hold-out ที่แท้จริงสำหรับการจูน `DEFAULT_REM_TUNING` (มีเฉพาะของ Q6) ⇒ มี over-fitting แน่นอน ตัวอย่างที่เห็นชัด: ลด `hrWindowEpochs` 10 → 6 ได้ F1 0.964 → 0.977 บนคืนจำลอง แต่ **ผมไม่เอา** เพราะ §5.2 ระบุ "ค่าเฉลี่ย 5 นาที" และ HR จริงมี noise มากกว่า ⇒ หน้าต่างยาวน่าจะทนกว่าในโลกจริง (บันทึกไว้เป็นปุ่มให้ R2 ลองใหม่)
4. **เกณฑ์ 0.70 ผูกกับการปรับเทียบของโมเดล** — `updateWeights` มีด่านกัน F1 ต่อคืน แต่ถ้าปรับหลายสิบคืนบวกกับข้อมูลจริง จุดทำงานจะเลื่อน ⇒ L2.9/L3 ควรคำนวณ threshold ต่อคนจากการกระจายของ p (เช่น เลือกจุดที่ precision ≈ 0.8) แทนเลข 0.70 ตายตัว
5. **โหมดไม่มีนาฬิกายิงไม่ได้เลย** (ดู §7.2) — ต้องตัดสินที่ L2.7
6. **`hist` ยังไม่มีใครป้อน** — `personalHistogram` เป็น option ที่รอ L2.9 · ค่าเริ่มต้น = ไม่มี = ฟีเจอร์ 0 ตรงตาม §5.2 ("เริ่มที่ 0 คืนแรก")
7. **ไม่มี fixture คืนจริงเหมือนเดิม** — ทุกตัวเลขในใบนี้มาจาก `simulateNight` ล้วน

## 7. ข้อแย้ง (พร้อมหลักฐาน — ไม่ได้แก้ข้อสอบ)

### 7.1 "ทุก epoch ในหน้าต่างต้อง motion ≤ 0.02" ใช้ไม่ได้ (แก้เป็นเกณฑ์ผ่อน)
ใบสั่งงานเขียนว่า onset = "20 epoch ล่าสุดมี motion ≤ 0.02 **ทุกตัว**" แต่ `simulate.ts` ใส่การกระตุกใน N2 ที่ `p = 0.08` ต่อ epoch ขนาด 0.02–0.15 g ⇒ โอกาสที่หน้าต่าง 20 epoch จะ "สะอาดทุกตัว" = `0.92²⁰ ≈ 19%` เท่านั้น การรอหน้าต่างสะอาดจริง ๆ ทำให้ onset ช้าเฉลี่ยครึ่งชั่วโมงและกระจายแบบ exponential (วัดจริงในรอบแรกที่ใช้เกณฑ์ `motionMove = 0.1`: 98 จาก 200 คืนประกาศช้ากว่า epoch 33 และ 96 ใน 98 คืนนั้นถูกบล็อกด้วย motion ไม่ใช่ HR)
**สิ่งที่ทำแทน**: ค่าเฉลี่ยในหน้าต่าง ≤ 0.04 g + กระตุกได้ ≤ 4 epoch + ห้ามมี epoch ≥ 0.25 g (ขนาด "ตื่น") ⇒ N4 (ขยับ 0.3 g ตลอด) ยังได้ `null` เพราะค่าเฉลี่ยเกินไปไกล · ผลรวม 99.5%

### 7.2 Q4 (p ≤ 0.75 เมื่อไม่มีเซนเซอร์) ขัดกับ DESIGN §5.1 (โหมดไม่มีนาฬิกา เกณฑ์ 0.75)
§5.1 เขียนว่า "โหมดไม่มีนาฬิกา: p_REM = prior เวลาอย่างเดียว · เกณฑ์สูงขึ้น 0.75 · สูงสุด 4 ครั้ง/คืน" แต่ข้อสอบ Q4 บังคับว่าคืนที่ไม่มีเซนเซอร์เลย **p ต้อง ≤ 0.75 ทุก epoch** ⇒ ถ้าทำตาม Q4 ตามตัวอักษร โหมดไม่มีนาฬิกาจะยิง cue ได้ก็ต่อเมื่อ `p = 0.75` เป๊ะ ๆ ซึ่งแปลว่า **ไม่มีวันยิงเลย**
- ตัวเลขของผมวันนี้: prior สูงสุด −0.923 ⇒ p สูงสุด **0.338** (ห่างจาก 0.75 มาก)
- ผมเลือกฝั่ง "หลับก่อน" ไว้ก่อนตามกฎ §0.2 ข้อ 9 (ไม่ดัน prior ขึ้นไปจ่อ 0.75) และ **ไม่ได้แก้ข้อสอบ**
- **ต้องให้ Fable ตัดสินที่ L2.7**: (ก) โหมดจับเวลาใช้เกณฑ์ของมันเอง เช่น "p สูงสุดของคืน" หรือ "ตารางเวลาคงที่ 4 ครั้งตามรอบ 90 นาที" แทนเลข 0.75 หรือ (ข) แก้ §5.1 ให้โหมดนี้ไม่ยิงเลย (= โหมดเก็บข้อมูลอย่างเดียว) — ทางเลือก (ก) ตรงเจตนาเดิมมากกว่า และ `remTimePrior()` ถูก export ไว้ให้ L2.7 เรียกตรงแล้ว

### 7.3 Q7 ทดสอบไม่ถึงเงื่อนไขของตัวเอง (ไม่บล็อก)
Q7 หา `idx` ของ epoch ที่ชั่วโมง UTC = 12 แต่คืนในข้อสอบเริ่ม 16:00 UTC ยาว 8 ชม. (16:00–24:00 UTC) ⇒ `idx = −1` เสมอ และ `if (idx >= 0)` ทำให้ไม่มีการ assert อะไรเลย · คอมเมนต์ในข้อสอบเองก็เขียนว่า "ช่อง 30 นาที: 12:30–13:30 UTC ≈ 19:30–20:30 ICT (ตัวอย่างเท่านั้น)" ⇒ น่าจะตั้งใจให้เป็นช่วง 04:30–05:30 ตามหัวข้อ (= 21:30–22:30 UTC = ช่อง 43–44)
ผมทดสอบเองด้วยช่องที่ตรงกับคืนนั้นจริง: ให้ช่องของ epoch แรก = 1.0 (ที่เหลือ 0.1) → p ของ epoch นั้นขึ้น **+0.133** · และฮิสโตแกรมแบน (ทุกช่องเท่ากัน) ให้ผลต่างจากไม่ใส่เลย = 0.000000 ตามที่ควรเป็น
**เสนอ**: ถ้า Fable อยากให้ Q7 กัดจริง เปลี่ยนช่องเป็น 43–44 (21:30–22:30 UTC) แล้วข้อสอบจะ assert ได้จริงโดยไม่ต้องแตะโค้ด engine

### 7.4 สัญญาในหัวข้อสอบ vs ของที่คืนจริง (ไม่บล็อก)
- `createOnsetDetector(...).feed()` หัวข้อสอบเขียน `{ onset, onsetT, baselineHr }` — ผมคืน `via` เพิ่ม (`SETTLED`/`DEEP`/`TIMER`) เพราะหน้ารายงานกลางคืนต้องบอกผู้ใช้ได้ว่า "รู้ว่าหลับจากอะไร" และ L2.7 ต้องรู้ว่าคืนนี้อยู่โหมดจับเวลาหรือไม่
- `updateWeights(w, truth, pRem, epochsFeatures?)` — ผมใช้ชื่อพารามิเตอร์ที่ 4 เป็น `{ epochs, onsetT, ... }` ตามใบสั่งงาน (ข้อสอบส่งมาแบบนี้พอดี) · ถ้าไม่ส่ง `epochs` มา ฟังก์ชันคืนน้ำหนักเดิมแทนที่จะเดาฟีเจอร์
- `DEFAULT_REM_WEIGHTS` มีคีย์ `eog: 2.5` เพิ่มจากตาราง §5.2 (ช่องหลักฐานที่ 5 ที่ §5.2 สั่งให้เผื่อไว้) — ผ่าน Q6 เพราะ 2.5 อยู่ใน [0,5] และฟีเจอร์เป็น 0 เสมอในวันนี้
