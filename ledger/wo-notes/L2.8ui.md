## 2. การตัดสินใจที่ไม่ได้เขียนไว้ตรง ๆ ใน WO

1. **`PLAY_CUE` ไม่เรียก `playNightCueIfAllowed`** (ที่ L1.7ui เตรียมไว้ให้) — ตัวนั้นจะถาม `cueGate` ซ้ำด้วย context ที่ต้องประกอบเองจากนอก engine ซึ่งเสี่ยงไม่ตรงกับของจริงข้างใน controller และอาจ "ปฏิเสธ" cue ที่ controller คอมมิตลง DB ไปแล้วว่า `played:true` (บั๊กที่แย่กว่าการไม่เช็กซ้ำเลย) ใช้ `controller.state === 'CUE'` แทน — เป็นค่าเดียวกับที่ engine เองใช้เป็นข้อบังคับ (§0.5 S7 "เล่นเสียง cue ได้เฉพาะตอน state เป็น CUE") ปลอดภัยเท่ากันแต่ไม่มีช่องให้สองแหล่งเห็นต่างกัน
2. **ตัวเลขข้าง "กระซิบครั้งที่ N"** ใน mockup 07 คือ **volume** ไม่ใช่ pRemAtCue (เห็นจาก mockup's caption "เวลา · ระดับ · ผล" + DESIGN "เริ่มที่ 15%") — เจอตอนเทียบภาพจริง เลขแรกที่ทำ (75/78/80% จาก pRemAtCue) ไม่ตรง mockup (15/18/18%) เปลี่ยนมาใช้ `cue.volume` แล้วตรงเป๊ะ
3. **`nextNightVolume`'s "current volume"** ใช้โวลุ่มของ **cue ล่าสุด** ไม่ใช่ cue แรก — ทำให้ "คงระดับ {n}%" ตรง mockup (18%) พอดี
4. **หัวข้อ "หยุด" จากนาฬิกา** (R8.7) เพิ่ม `onCommand` ให้ `watchBridge.ts`/`WatchSensorSource.ts` (ทิศทางนาฬิกา→มือถือ ของเดิมมีแค่ `sendCommand` มือถือ→นาฬิกา) — ยังเป็น honest stub เหมือนเพื่อนบ้าน (native module ไม่มี ตาม L1.1's เดิม)
5. **`AudioPlayer.startBed`** เพิ่มพารามิเตอร์ `source` (optional, ไม่พัง diagnostics.tsx เดิม) — คืนจริงต้องเล่น ambience ตามแผน (`ambienceSource(plan.ambienceKey)`) ไม่ใช่ก้อนเสียง diagnostic คงที่
6. **แถวเหตุการณ์ "SEED"** — `session.ts`'s `WHISPER_SEED` handler เขียน `CueEvent` แถว `type:'SEED'` ลง DB ด้วย (ไม่ใช่แค่ log) เพราะ `repo.ts#buildEvents` เขียนไว้ชัดว่าคาดหวังแถวนี้อยู่แล้ว (`cue.type.toUpperCase()==='SEED'`) — ไม่งั้นแถว "ปลูกภาพ" ในรายงานจะหายไปตลอด
7. **12 รายการ ไม่ใช่ 11** ในรายงาน — mockup รวม "ตื่น · เล่าฝัน 0:42 · ตอบ 4 ข้อ" เป็นแถวเดียว ผมแยก `END`/`REPORT` เป็น 2 แถว เพราะไม่มีฟิลด์ระยะเวลาบันทึกเสียง/จำนวนคำตอบเก็บอยู่ใน schema จริง (ReportRecord ไม่มี audio duration) — แต่งตัวเลขนั้นขึ้นมาจะผิดกติกา "ห้ามแต่งข้อมูล"
8. **ปุ่ม "ส่งออก"** ใช้ `repo.diagnosticsDraft({sessionId})` (comment ของ `repo.ts` เองชี้ว่านี่คือปุ่มนี้) ไม่ใช่ `exportJson` (dump ทั้ง DB) — `exportNightJson/Csv` ยังเขียนไว้ใน `src/data/report.ts` (เผื่อ WO ถัดไปอยากได้) แต่ไม่ผูกกับหน้าจอนี้

## 5. ข้อขัดแย้ง/สิ่งที่ตีความเอง (แจ้ง Fable)

- WO บอกให้ใช้ `HealthImport.readSleepStages(dateRange)` — อินเตอร์เฟซจริงที่ L1.3 วางไว้แล้วชื่อ `fetchSleepPhases(range: {fromIso,toIso})` (มี `SleepPhase` type ครบพร้อม) ใช้ของเดิมแทนที่จะสร้างชื่อใหม่ซ้อนกัน (สอดคล้องกับ platform bundle ที่มีอยู่)
- WO บอก "Live: run with a simulated feed จาก `simulateNight` เมื่อ `?fixture=night`" — ตีความว่าป้อนจนถึงจุดที่มีอะไรให้ถ่ายภาพ (pRem≥60% + กระซิบ≥2 ครั้ง) แล้วหยุด ไม่ใช่ป้อนครบ 8 ชม. จริง (ไม่งั้นภาพจะสุ่มว่าจะหยุดที่ state ไหนก็ได้ ไม่รับประกันว่ามีอะไรให้ดู)
- ตัวเลขข้าง "กระซิบครั้งที่ N" (ดู §2 ข้อ 2) — ของเดิมที่ผมเข้าใจผิดตอนแรกคือ pRemAtCue เพราะ `ledger/wo-notes/L2.6-2.7.md`'s หนี้ข้อ 5 ("pRemAtCue = 0 ในโหมดจับเวลา … ต้องแสดงเป็น '—' ไม่ใช่ 0%") พูดถึงแถวกระซิบในบริบทเดียวกัน ทำให้ชวนคิดว่าตัวเลขที่โชว์คือ pRemAtCue — แก้แล้วตามที่ตรวจกับภาพจริง (mockup's ตัวเลขคือ volume; หนี้ pRemAtCue=0→'—' ยังใช้จริงแต่ย้ายไปอยู่ที่แถว `REM_LIKELY` แทน)
