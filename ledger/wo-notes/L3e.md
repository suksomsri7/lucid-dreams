## 1. `ble.ts` — parser Heart Rate Measurement (0x2A37)

### 1.1 ตารางบิตของ flags (ไบต์ 0) และลำดับไบต์

| บิต | ค่า | ความหมาย | ผลต่อการอ่านไบต์ |
|---|---|---|---|
| 0 | `0x01` | รูปแบบ bpm | 0 = uint8 (1 ไบต์) · 1 = **uint16 little-endian** (2 ไบต์) |
| 1 | `0x02` | สัมผัสผิวหนังอยู่ | อ่านได้เฉพาะเมื่อบิต 2 = 1 |
| 2 | `0x04` | อุปกรณ์รองรับการตรวจสัมผัส | บิต 2 = 0 ⇒ `sensorContact = null` (ไม่ใช่ `false`) |
| 3 | `0x08` | มีฟิลด์ energy expended | uint16 little-endian หน่วย **kJ** ต่อหลัง bpm |
| 4 | `0x10` | มีฟิลด์ RR intervals | uint16 ละ 1 ค่า หน่วย **1/1024 วินาที** ต่อท้ายสุด |
| 5–7 | — | reserved | ไม่อ่าน |

ลำดับ: `flags → bpm(1–2) → energy(2 ถ้าบิต 3) → RR(2×n ถ้าบิต 4)` · ฟิลด์เป็น **ตำแหน่ง** ไม่ใช่ชื่อ ⇒ ไบต์หายหนึ่งไบต์ไม่ได้ทำให้ค่าหนึ่งค่าหาย แต่ทำให้ค่าถัดไป **ทั้งหมดเลื่อน** จึงต้องทิ้งทั้งใบ

ตัวอย่างที่ข้อสอบใช้ (ตรงกับที่ implement)

| ไบต์ | อ่านได้ |
|---|---|
| `00 3E` | bpm 62 · contact `null` · rr `[]` |
| `01 3E 00` | bpm 62 (16 บิต) |
| `01 2C 01` | bpm 300 → **null ทั้งใบ** (นอกช่วง 25–220) |
| `06 3C` / `04 3C` / `00 3C` | contact `true` / `false` / `null` |
| `18 3C 10 00 00 04` | bpm 60 · energyKj 16 · rr `[1000]` |
| `10 3C 00 04 33 03` | rr `[1000, 799.805]` (0x0333=819 → 819×1000/1024) |

### 1.2 กฎ "ไม่เชื่อ payload" (§0.5 S8)

- คืน `null` ทั้งใบเมื่อ: บัฟเฟอร์ < 2 ไบต์ · ตั้งบิต 0 แต่มีไบต์ไม่ถึง 3 · ตั้งบิต 3 แต่ไบต์ไม่พอ 2 ไบต์ · **bpm นอก 25–220** (`HR_MIN_BPM`/`HR_MAX_BPM` จาก `diagnostics.ts` ไม่ตั้งเลขใหม่)
- ผ่อนปรน 1 อย่างตั้งใจ: ไบต์เศษ **คี่ท้ายบล็อก RR** ให้ข้าม ไม่ทิ้งทั้งใบ — RR อยู่ท้ายสุด ไบต์เศษไม่เลื่อนอะไร และการทิ้ง HR ดี ๆ เพราะ padding ของ HRV ไม่คุ้ม
- RR แต่ละค่าที่ไม่อยู่ใน `RR_MIN_MS`(250)–`RR_MAX_MS`(3000) **ทิ้งเป็นค่า ๆ ไป** (บีตตกบนสายหลวมเป็นเรื่องปกติ) — ห้ามให้ค่าเพี้ยนเข้า RMSSD เพราะ RMSSD ยกกำลังสองผลต่าง

### 1.3 HRV

- `rmssd(rrMs)` = √(Σ(diff²)/จำนวนคู่) หน่วย ms · ต้องมี ≥ 2 บีต ไม่งั้น `null` (ไม่ใช่ 0 — "ไม่มีข้อมูล" กับ "หัวใจนิ่งสนิท" ต้องไม่หน้าตาเหมือนกันสำหรับตัวประเมิน §5.2)
- `sdnn(rrMs)` = SD แบบ **ประชากร (÷ n)** ไม่ใช่ตัวอย่าง (÷ n−1) — ช่วง 30 วิ คือประชากรทั้งก้อนของ epoch นั้น และ ÷(n−1) จะพองค่าตรงที่ข้อมูลน้อยที่สุดพอดี · ข้อสอบ B7 ยืนยัน: `sdnn([900,1100]) = 100`

## 2. `SensorHub` — กฎการรวมหลายแหล่ง (DESIGN §8.1)

`createSensorHub({ epochSeconds = 30 })` → `push(sourceId, sample)` · `closeEpoch(tEnd)` · `sources()`

| ฟิลด์ของ epoch | กฎ | เหตุผล |
|---|---|---|
| `t` | `tEnd − epochSeconds` (ปิดหน้าต่าง `[t, tEnd)`) | epoch ที่ปิด "ลงท้ายที่ tEnd" ตามที่ผู้เรียกถือเวลาอยู่ ไม่ต้องให้ผู้เรียกคำนวณกริดเอง |
| `hrMean` | เฉลี่ย**ถ่วงจำนวน sample** (ไม่ใช่เฉลี่ยของอุปกรณ์) | สายคาดอกส่งวินาทีละครั้ง นาฬิกาส่ง 5 วิครั้ง — ถ่วงด้วยจำนวน sample = ถ่วงด้วยปริมาณหลักฐาน |
| `hrSd` | ถ้ามี RR ≥ 2 ค่า: SD ของ HR ชั่วขณะ `60000/rr` · ถ้าไม่มี RR: SD ของ bpm | หน่วยของ `hrSd` ในสคีมาคือ bpm จึงแปลง RR เป็น bpm ก่อน ไม่ปล่อย ms ปนหน่วย · RR jitter เป็นสัญญาณ REM ที่ดีกว่าการกระจายของ bpm ที่ถูกเฉลี่ยมาแล้ว |
| `motion` | **max** | การขยับเป็นหลักฐานว่า "ตื่น" — มือถือที่นอนนิ่งบนที่นอนต้องไม่เฉลี่ยข้อมือที่ดิ้นให้หายไป |
| `battery` | **min** ของค่าที่ไม่ null | จอ diagnostics ถามว่า "ชุดนี้รอดถึงเช้าไหม" คำตอบคืออุปกรณ์ที่อ่อนที่สุด |
| `source` | kind ของแหล่งที่ให้ **HR มากสุด** · เสมอ → ตัวที่ส่ง RR ด้วย → ตัวที่ push ก่อน | สคีมามีช่องเดียว จึงให้หมายถึง "พยานหลัก" ของ epoch นั้น |
| คืน `null` | ไม่มี sample ที่ใช้ได้ในหน้าต่างเลย | โหมดตัวจับเวลา/ช่วงหลุดต้องแยกออกจาก "หลับนิ่งมาก" |

กฎกันซ้ำ/ย้อนเวลา (§0.5 S8)
- `(sourceId, t)` รับครั้งเดียว — สายคาดอกที่หลุดแล้วต่อใหม่จะ replay บัฟเฟอร์ ถ้าไม่กันจะนับวินาทีเดิมสองเท่า (ข้อสอบ H1 push ซ้ำทุก sample)
- sample ที่ `t < ` ปลาย epoch ที่ปิดไปแล้ว **ถูกปฏิเสธ** — epoch ที่ส่งออกไปแล้วเขียนทับไม่ได้
- `bpm` นอกช่วงถูกตัดออกจาก sample (ไม่ทิ้ง motion/battery ที่มาในใบเดียวกัน) แต่ถ้าตัดแล้วเหลือ "ไม่มีข้อมูลอะไรเลย" ให้ทิ้งทั้ง sample ไม่ให้ไปทำให้ epoch ที่ควรเป็น `null` ดูเหมือนมีข้อมูล
- key ของตัวกันซ้ำถูกตัดทิ้งเมื่อพ้นหน้าต่าง (ไม่โตไม่สิ้นสุดตลอดคืน)
- ทุก epoch ที่ออก **ผ่าน `SensorEpochSchema`** (clamp hrMean 25–220 · hrSd 0–80 · battery 0–1 · `t` จำนวนเต็ม ≥ 0) — ข้อสอบ H3

## 3. `aiScore.ts` — สคีมา · ตัวกรอง · ข้อความเช้า

### 3.1 สคีมา (DESIGN §6)
`themeMatch` int 0–10 · `matchedTerms` ≤ 8 (คำละ ≤ 80 ตัว) · `lucidSignals {present, quote|null}` · `tags` ≤ 5 · `summary` ≤ 240 · `model?` — **ฟิลด์แปลกถูก strip** (zod strip ตามค่าเริ่มต้น) ไม่ใช่ reject: โมเดลพูดมากยังใช้ได้ แต่คีย์ `volume`/`command` ที่โมเดลถูกสั่งให้ใส่ (prompt injection) หายเงียบ ๆ ไม่มีที่ลง (§0.5 S3) · ในสคีมานี้ **ไม่มีฟิลด์ใดสั่งแอปได้เลย**

### 3.2 กติกาของ `sanitizeAiScore(raw, transcript)`
1. `safeParse` ไม่ผ่าน → **`null` ทั้งใบ** ⇒ ต้นทางแสดง "คะแนนผู้ใช้อย่างเดียว" (DESIGN §6 · APP-RUN L3.2)
2. `matchedTerms` ที่หาไม่พบใน transcript → **ตัดทิ้ง** · เทียบแบบ **ลบช่องว่างทั้งหมด + lowercase** เพราะภาษาไทยไม่เว้นวรรค: โมเดลเขียน `ตัวใหญ่ สีเทา` กับคนเล่าว่า `ตัวใหญ่สีเทา` คือคำเดียวกัน ช่องว่างต้องไม่ใช่สาเหตุที่ลบคำที่ตรงจริงทิ้ง · ตัดคำซ้ำด้วย
3. `lucidSignals.quote` ที่ไม่ใช่ข้อความในนั้น → `null` แต่ **`present` ไม่ถูกล้าง** — โมเดลอาจเห็นจังหวะรู้ตัวจริงแล้วเรียบเรียงคำใหม่: สัญญาณอยู่ ถ้อยคำที่แต่งไป
4. ไม่เคยโยน exception และไม่เคย "ซ่อม" ใบที่พัง — คะแนนที่เดาครึ่งใบแย่กว่าไม่มีคะแนน
5. ข้อความ injection ใน transcript ไม่มีผลต่อ `themeMatch`/`tags`/`summary` (ข้อสอบ C3) เพราะ transcript เข้ามาเป็น **ข้อมูลที่ใช้ตรวจ** ไม่ใช่ข้อความที่ถูกตีความ

## 4. `bandit.ts` — เลขคณิตของ Learning loop (§5.5)

### 4.1 arm space + reward
- `ARMS` = volume {0.12, 0.18, 0.24} × delaySec {60, 120, 180} × cueType {WHISPER, TONE_PHRASE, AMBIENCE_SWELL} = **27** · `armKey` = `v0.18/d120/WHISPER` (อ่านออกด้วยตา เพราะคีย์นี้ไปอยู่ใน `PersonalModel` บนเครื่องและใน log ของงานซัพพอร์ต — index ตัวเลขจะเปลี่ยนความหมายเงียบ ๆ เมื่อรายการ arm โต)
- `nightReward` = (YES 1 · UNSURE 0.3 · NO/null 0) + 0.3×themeMatch/10 − 0.5×ปลุก − 0.3×(หลับดี < 5) → ช่วงจริง **−0.8 … 1.3** · **ไม่ clamp ที่นี่** เพราะเทียบคืนต่อคืนแล้วมีความหมาย ไปclamp ตรงจุดที่จำเป็นคือ `update`
- คำตอบที่ขาด (null) = 0 ไม่ใช่เดาค่า — เช้าที่ไม่ตอบแบบฟอร์มต้องไม่หน้าตาเหมือนคืนที่ดี

### 4.2 Thompson sampling
- Beta(a,b) ต่อ arm เริ่ม (1,1) หรือจาก `prior` ประชากร (a,b ≤ 0/ไม่ใช่เลข → ตกกลับ 1,1)
- `pick()` = จับ 1 ตัวอย่างต่อ arm แล้วเอา argmax (เสมอ → arm ที่มาก่อน ⇒ seed เดียวกันได้ผลเดิมเสมอ)
- ตัวอย่าง Beta มาจาก **Gamma 2 ตัว**: `X/(X+Y)`, `X~Γ(a)`, `Y~Γ(b)` — ไม่มี inverse CDF ของ Beta แบบปิดรูปให้ใช้ · Gamma ใช้ **Marsaglia–Tsang (2000)** · shape < 1 ใช้ตัวคูณมาตรฐาน `Γ(a) = Γ(a+1)·U^(1/a)` · normal มาจาก **Box–Muller** ที่ป้อนด้วย uniform ของ rng ที่ฉีดเข้ามา ⇒ ทุกการจับสลากอยู่ใน seed เดียว (replay ได้ ตาม §0.2 ข้อ 6)
- `update(arm, reward01)`: **clamp [0,1]** แล้ว `a += r`, `b += 1−r`, `nights += 1` — Beta คือความเชื่อเกี่ยวกับ *ความน่าจะเป็น*: reward 1.3 คือ "คืนแบบที่ดีที่สุด" ไม่ใช่ "สำเร็จ 130%" และ −0.8 คือ "แย่ที่สุด" ไม่ใช่หลักฐานลบที่เอาไปหักจำนวนนับ
- **คืนควบคุมไม่มี flag ในไฟล์นี้** — ตัวควบคุมแค่ไม่เรียก `update` (ไม่มีอะไรให้ตั้งผิด) · `posterior()` คืน**สำเนา** ⇒ arm ที่ไม่ถูกอัปเดตเท่าเดิมทุกไบต์ (ข้อสอบ B5)

### 4.3 `PICK_SHARPENING = 3` — จุดที่ตำราไม่พอสำหรับสินค้านี้ (⚠️ ตัดสินใจเอง ขอให้ Fable ทบทวน)
Thompson sampling แท้ ๆ บน **27 arms** ที่ prior แบน `Beta(1,1)`: ค่า **สูงสุด** ของ 26 ใบที่ยังไม่รู้จักอยู่ราว 26/27 ≈ 0.96 ทุกคืน ⇒ prior ประชากรที่แรงถึง `Beta(30,3)` (ค่ากลาง 0.91) ชนะคืนแรกแค่
`E[X^26] = B(56,3)/B(30,3) = (32·31·30)/(58·57·56) = 16.1%` — แปลว่าสัปดาห์แรกแอป**ทิ้งข้อมูลประชากรแล้วสุ่มมั่ว** ซึ่งเป็นการเอาคืนนอนของคนจริงไปจ่ายค่า exploration

จึงสุ่มจาก `Beta(a·k, b·k)` (คม k = 3 · ค่ากลางไม่ขยับ แค่การกระจายแคบลง) วัดจริงด้วย `.heavy/verify-sharpen.mts` (4,000 seed/ค่า):

| k | prior ดีชนะ pick แรก |
|---|---|
| 1 (TS แท้) | **14.9%** (ตรงกับเลขวิเคราะห์ 16.1%) |
| 2 | 55.9% (คาบเส้นเกณฑ์ 50% ของข้อสอบ B6) |
| **3 (เลือกใช้)** | **83.1%** |
| 4 | 93.3% |

และ exploration ยังพอ: จำลอง 500 คืนแบบข้อสอบ B3 (arm ดีจริง 0.7 · ที่เหลือ 0.25) ได้ส่วนแบ่ง 100 คืนท้าย **0.93–1.00** จาก 6 seed (เกณฑ์ ≥ 0.70) · เป็นการเอียงเข้าหา prior อย่างตั้งใจ และป้องกันได้เพราะ prior คือข้อมูลจริงของประชากร ไม่ใช่ค่าที่ตั้งลอย ๆ

### 4.4 `PersonalModel` + คำอธิบาย
- `topArm` = ค่ากลาง posterior สูงสุด (เสมอ → arm ที่มีหลักฐานมากกว่า → ลำดับ `ARMS` คงที่) ⇒ โมเดลไม่กะพริบสลับสอง arm ที่เท่ากัน
- `confidence` (0–1) = **หลักฐาน × การแยกตัว** เพราะคนถามว่า "มั่นใจแค่ไหน" หมายถึงทั้งสองอย่างพร้อมกัน
  - หลักฐาน = `min(nights/14, 1)` ⇒ 3 คืนจะอ่านว่ามั่นใจไม่ได้เลยแม้โชคดี
  - การแยกตัว = `(ค่ากลางที่ 1 − ค่ากลางที่ 2) / (2·√(var₁+var₂))` clamp 0–1 (ห่าง 2 SD = แยกเต็ม)
- `volumeCeiling` = clamp(ceiling ที่ผู้ใช้ตั้ง, 0.08, **0.35**) — เพดาน §0.5 S6 อยู่ในเครื่องยนต์ ไม่เชื่อค่าจาก UI · `suggestedVolume` = min(volume ของ topArm, เพดาน) ⇒ **ไม่มีทางเสนอ volume นอก 8–35%**
- `learning = nights < 14` ⇒ หน้าสถิติแสดง "กำลังเรียนรู้ n/14" ตาม §5.5
- `explainLearning(model, lang)` — ภาษาคนล้วน ไม่มีคำเทคนิคแม้แต่คำที่เรียกตัวเลือก (ข้อสอบ B8 แบน `thompson|beta|posterior|arm` ⇒ ภาษาอังกฤษต้องระวังคำที่มี "arm" ซ่อน เช่น warm/alarm/harm ด้วย) · ชื่อชนิดเสียงแปลเป็นคำคน: WHISPER = "เสียงกระซิบเบา ๆ" · TONE_PHRASE = "เสียงโน้ตสั้นแล้วค่อยพูดประโยค" · AMBIENCE_SWELL = "เสียงบรรยากาศที่ดังขึ้นช้า ๆ" · delay เป็นนาที
  ```
  กำลังเรียนรู้ 13/14 คืน — สิ่งที่เข้ากับคุณที่สุดคือเสียงโน้ตสั้นแล้วค่อยพูดประโยค ที่ระดับ 12% เปิดหลังเริ่มฝันประมาณ 1 นาที · ยังไม่แน่ใจ ขอเวลาอีกหน่อย
  Over your last 40 nights — what suits you best is a short note, then the sentence at 18%, about 2 minutes after the dream starts · I am fairly sure of that now
  ```
  เหตุผลที่ห้ามศัพท์: ประโยคที่ผู้ใช้ตรวจไม่ได้ คือประโยคที่เขาเถียงไม่ได้ และฟีเจอร์นี้ทำงานได้ก็เพราะเขาเถียงได้ว่า "ไม่ใช่ คืนนั้นแย่เพราะหมาข้างบ้าน"

### D-1 `L2.3-ble.test.ts:16` (B2) — **บรรทัดนี้ผ่านไม่ได้ด้วย implementation ใด ๆ**
```ts
expect(parseHeartRateMeasurement(u8(0x01, 0x2c, 0x01)).bpm).toBe(300 > 220 ? undefined : 300);
expect(parseHeartRateMeasurement(u8(0x01, 0x2c, 0x01))).toBeNull();     // ← บรรทัดถัดไปในข้อเดียวกัน
```
บรรทัดแรกอ่าน `.bpm` จากค่าที่บรรทัดที่สองบังคับว่าต้องเป็น `null` พอดี · ใน JS การอ่าน property จาก `null` โยน `TypeError` เสมอ และไม่มีค่าใดที่ `expect(x).toBeNull()` ผ่าน (ต้อง `Object.is(x, null)`) พร้อมกับให้อ่าน `.bpm` ได้ ⇒ **ข้อสอบข้อนี้ขัดกันเอง** · หลักฐาน: `TypeError: Cannot read properties of null (reading 'bpm')` ที่ `test/L2.3-ble.test.ts:16:109`

### D-2 `L3.4-bandit.test.ts:28` และ `:31` (B3 · B4) — ข้อสอบเรียก `rng()` แต่ `mulberry32` คืน **object**
```ts

```
`rng.ts` (ของ L2.1 · ห้ามแตะในใบนี้) ประกาศ `mulberry32(seed): Rng` ที่มี `next()/range()/int()/bool()/normal()/pick()/shuffle()` — เรียก `rng()` ตรง ๆ ไม่ได้ · ข้อสอบ L2.6 ใช้แบบเดียวกันแต่ส่งต่อเป็น `rng` เฉย ๆ ไม่ได้เรียก จึงไม่เคยโป๊ะ

## 6. หนี้ / ของที่ยังไม่ได้ทำ (ส่งต่อ)

1. **`AMBIENCE_SWELL` vs `AMBIENCE_UP`** — `types.ts` `CueType` คือ `WHISPER|SPOKEN|TONE_PHRASE|AMBIENCE_UP` แต่ข้อสอบ L3.4 บังคับชื่อ `AMBIENCE_SWELL` และไม่มี `SPOKEN` ใน arm space · ไม่แก้ `types.ts` (นอกขอบเขต) แต่มี `playerCueType(arm)` แปลงให้ชั้นเสียงในที่เดียว — ควรรวมคำศัพท์ให้เหลือชุดเดียวในใบที่ถือ `types.ts`
2. **ต่อสายเข้าของจริงยังไม่ทำ** (เป็นงานฝั่งแอปของ L2.3/L3.2/L3.4 ไม่ใช่ engine): `react-native-ble-plx` scan `0x180D` + reconnect · `expo-sensors` มือถือบนที่นอน · `/ai/score` + rate limit + ขนาด body (§0.5 S2) · การบันทึก/โหลด `PersonalModel` ลง SQLite · `nextNightVolume` ของ L2.6 ยังไม่ถูกแทนด้วย `suggestedVolume` ของโมเดล
3. **prior ประชากรยังไม่มีตัวเลขจริง** — `createBandit({prior})` รับได้แล้ว แต่ค่าเริ่มต้นคือ `Beta(1,1)` ทุก arm · ต้องมีชุดตัวเลขจากเซิร์ฟเวอร์ (หรือค่าที่เจ้าของเคาะ) ก่อนจะได้ประโยชน์จาก §4.3
4. **`confidence` ยังไม่ใช่ความน่าจะเป็นจริง** — เป็นดัชนี 0–1 ที่อธิบายได้ (หลักฐาน × การแยกตัว) ไม่ใช่ `P(topArm ดีที่สุด)` แบบ Monte Carlo · ถ้าหน้าสถิติจะโชว์เป็น "%" ต้องเปลี่ยนเป็นการสุ่มนับ (ต้องใช้ rng) หรือเปลี่ยนคำในหน้าจอ
5. **คำห้ามยังเป็นรายการคำ** — ไม่ใช่ตัวตรวจความหมาย · ถ้าเปิดสรุปรายสัปดาห์จาก AI (§6 แถวสุดท้าย) ต้องยิงข้อความนั้นผ่าน `containsForbiddenClaim` ก่อนแสดง และควรเพิ่มคำตามภาษาที่รองรับเพิ่ม
6. **`sanitizeAiScore` ไม่ตรวจ `tags`/`summary` กับ transcript** — ตามสัญญา (ข้อสอบ C3 ตรวจว่า summary ไม่เปลี่ยนรูปแบบเมื่อมี injection) แต่หมายความว่า tag ที่โมเดลแต่งขึ้นยังหลุดได้ · ถ้าจะปิดช่องนี้ต้องมีกติกาใหม่ (เช่น tag ต้องมาจากรายการปิด) — รอเจ้าของเคาะ
