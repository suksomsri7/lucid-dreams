## 2. ตัวสร้าง hypnogram — ออกแบบอย่างไร

### 2.1 โครงคืน (แผนเป็น "ช่วง" ก่อน แล้วค่อยกางเป็น epoch)

```
[N1 สั้น → N2]        = ช่วงกำลังหลับ (sleep onset latency 5–25 นาที · สุ่ม)   onsetT = จบช่วงนี้
[รอบที่ 1..n]          แต่ละรอบ = N2a → N3 → N2b → (N1 1 epoch) → REM
[WAKE 3–8 นาที]        ตื่นเช้า ปิดท้ายทุกคืน
```

ตัวเลือกออกแบบที่สำคัญ 4 ข้อ:

1. **จำนวนรอบคิดจากเวลาที่เหลือ** `nCycles = clamp(round(sleepEpochs / cycleMin), 3, 8)` แล้ว **normalize ความยาวรอบให้ผลรวมเท่ากับเวลาที่เหลือพอดี** — jitter (±10 นาที) จึงเป็นตัวตัดสินว่า "รอบไหนยาวกว่ากัน" ไม่ใช่ "คืนยาวเท่าไร" ⇒ ไม่มีรอบท้ายที่ถูกตัดกลางคัน และ `epochs.length = durationMin × 2` เสมอ (E3)
2. **REM คิดเป็นงบก่อน แล้วค่อยแบ่งลงรอบ** — `remBudget = round(remFraction × epochCount)` โดย `remFraction` สุ่ม 0.205–0.245 แล้วแจกตามน้ำหนักรอบ `[1, 1.75, 2.3, 2.5, 2.45, …]` (REM ยาวขึ้นเรื่อย ๆ) พร้อมเพดาน/พื้นต่อรอบ (รอบแรก 7–13 นาที · รอบหลัง 15–40 นาที) ถ้าเพดานไปตัดของรอบไหน **ส่วนที่ขาดถูกย้ายไปรอบอื่นที่ยังมีที่ว่าง** ⇒ สัดส่วน REM ทั้งคืนคุมได้แน่นอน ไม่ใช่ "หวังว่าจะออกมาพอดี" (E4 · E9)
3. **REM latency บังคับด้วยเพดานของรอบแรก**: `rem₀ ≤ len₀ − 62 นาที` ⇒ REM ก้อนแรกเริ่มช้ากว่า onset ≥ 62 นาทีโดยโครงสร้าง ไม่ได้อาศัยความน่าจะเป็น (E5) — เผื่อ 2 นาทีจากเกณฑ์ 60 ไว้กันปัญหาปัดเศษ
4. **ตื่นกลางคืนใช้วิธี "ทับ" ไม่ใช่ "แทรก"** — เขียน WAKE ทับ epoch ของ N2 ที่อยู่ห่าง onset ≥ 60 นาที ⇒ คืนยังยาวเท่าเดิมเป๊ะ และ **งบ REM ไม่ถูกแตะ** (ถ้าแทรก ความยาวคืนจะเลื่อนและสัดส่วนทุกอย่างเพี้ยน) · เลือกตำแหน่ง "ท้าย REM" ก่อน (รอบท้าย ๆ ก่อน) แล้วค่อยที่อื่น · หลังตื่นกลับเข้านอนผ่าน N1 1–2 epoch เสมอ · เพดาน WAKE ทั้งคืน (รวมตื่นเช้า) = 11.5% ของคืน

### 2.2 สมมติฐานสรีระ + ที่มา

ตัวเลขทุกตัวเป็น **ค่ากลางของผู้ใหญ่สุขภาพดี** ที่ใช้กันในตำราเวชศาสตร์การนอน ผมอ้างจากความรู้ในตำราต่อไปนี้ (ครั้งนี้ **ไม่ได้เปิดเว็บ/ไม่ได้ดึงตัวเลขจากไฟล์งานวิจัยจริง** — จึงไม่ใส่เลขหน้า/DOI เพื่อไม่ให้เป็นการอ้างอิงลอย ๆ ตามกติกา "ห้ามแต่งข้อมูล"):

| เรื่อง | ค่าที่ใช้ | ที่มา / เหตุผล |
|---|---|---|
| นิยามสเตจ · epoch 30 วิ | WAKE/N1/N2/N3/REM | AASM Scoring Manual (Apple รวม N1+N2 เป็น `CORE` ⇒ L2.9 จะ map เอง) |
| รอบ NREM–REM | ~90 นาที (±10) · 4–6 รอบ/คืน | Carskadon & Dement, "Normal Human Sleep: An Overview" (Principles and Practice of Sleep Medicine) |
| REM latency | 70–110 นาทีหลัง onset (ผมตั้งพื้น 62 นาที) | แหล่งเดียวกัน — และเป็นเหตุผลที่ Sleep Guard 3 ชม.แทบไม่เสีย REM ก้อนสำคัญ |
| REM ก้อนแรกสั้น ~10 นาที · ก้อนหลัง 20–40 นาที | น้ำหนัก `[1, 1.75, 2.3, 2.5, 2.45]` | แหล่งเดียวกัน (REM ยาวขึ้นตามรอบ · หนาแน่นครึ่งหลัง) |
| N3 กระจุกครึ่งแรก | สัดส่วน N3 ต่อ NREM ในรอบ = 45% / 35% / 18% / 6% / 2% | แหล่งเดียวกัน (slow-wave sleep ถูก "จ่าย" หมดในสองรอบแรก) |

| HR ต่อสเตจ | ฐาน 58 bpm (สุ่มต่อคืน 48–70) · N3 −5 · N2 0 · N1 +2 · REM +3 · WAKE +10 · ไหลลงอีก ~1 bpm ตลอดคืน | Trinder et al. และงานตระกูล cardiac autonomic activity across sleep stages: HR ต่ำสุด/สม่ำเสมอสุดใน N3 · สูงขึ้นและ **ไม่สม่ำเสมอ** ใน REM |
| ความแปรปรวน HR ในช่วง epoch (`hrSd`) | N3 ~1 · N2 ~2 · N1 ~2.5 · REM 4–6 (สุ่มต่อ epoch) · WAKE ~6 bpm | แหล่งเดียวกัน — **นี่คือหลักฐานที่มือข้อมือเห็นชัดที่สุดว่าเป็น REM** (DESIGN §5.2 น้ำหนัก 1.2) |
| ขยับ (accel energy, g) | WAKE 0.2–0.6 · N1 0.006 · N2 0.004 · N3 0.005 · REM 0.003 + twitch โอกาส 2% (0.02–0.08 g) | วรรณกรรม actigraphy ของ wrist tracker: REM แทบนิ่งเพราะ atonia แต่มี twitch สั้น ๆ · WAKE แรงกว่าเป็นสิบเท่า |
| แบต | เริ่ม 0.86–0.93 ลดเชิงเส้นถึง ~0.60 (ปัดขั้น 1%) | สมมติฐานตั้งต้นเพื่อให้ R1 เอาไปเทียบของจริง — ยังไม่มีข้อมูลนาฬิกาเจ้าของ |

`noise` (ค่าเริ่ม 1) คูณเฉพาะ **ความกระจาย** ไม่แตะค่ากลาง ⇒ `noise: 3` (E8) ได้คืนที่สัญญาณเลอะแต่รูปร่างเดิม · ทุกค่าถูก clamp ให้อยู่ในช่วงที่ `SensorEpochSchema` รับ (HR 26–210 · hrSd 0.1–60 · motion 0.0005–3 · battery 0–1) และฟังก์ชัน `clamp` คืนค่าขอบเมื่อเจอ NaN ⇒ **เป็นไปไม่ได้ที่ epoch จะมี NaN**

## 4. replay + metrics

**`replayNight(diag)`** — สัญญาคือ **ห้าม throw** ทุกกรณี: ถ้า `diag` ไม่ใช่วัตถุที่มี `epochs` เป็น array (null / 42 / `{}` / `{epochs:'x'}`) คืน `[]` · แถวที่ไม่ผ่าน `SensorEpochSchema` ถูกทิ้งทีละแถว (ผมใช้ `safeParse` ต่อแถว ไม่ parse ทั้งก้อน) แล้วส่งที่เหลือเข้า `normalizeEpochs` เดิม (เรียง · dedupe ตาม index ของกริด · แถวหลังทับแถวก่อน) · `replayNightReport()` คืน `{raw, invalid, duplicates}` ให้คนอ่าน QC เห็นว่าไฟล์เสียแค่ไหน — ตัวเลขชุดนี้คือของที่ R1 ต้องรายงาน

ตรวจ round-trip เพิ่มเอง: คืนจำลอง (มี dropout 5%) → `buildDiagnosticsExport` → `JSON.parse(JSON.stringify())` → `parseDiagnostics` → `replayNight` = **เท่าเดิมทุกไบต์ 960 epoch** · `epochCoverage` = `{count:960, expected:960, continuity:1, gaps:0, duplicates:0}`

**`remMetrics(truth, pRem, threshold=0.7)`** — กติกาที่สำคัญกว่าสูตร: (1) เทียบเฉพาะ `t` ที่ตรงกันเป๊ะ — `p` ที่ไม่มีเฉลย **ไม่นับเป็น fp** เพราะ "ไม่มีเฉลย" ไม่ใช่ "ทายผิด" (E14) · (2) ตัวส่วน 0 ⇒ ผลเป็น **0 ไม่ใช่ NaN** ทุกตัว (ถ้า NaN หลุดออกไปหน้าสถิติจะโชว์ "NaN%" ให้ผู้ใช้เห็น) · (3) `p` ซ้ำ `t` เดิม ตัวหลังทับตัวก่อน เหมือนกติกา epoch จะนับซ้ำไม่ได้ · (4) `p` ที่เป็น NaN/Infinity ถูกข้าม

## 5. CLI + ผลจริงของตัวจำลอง

```bash

```

## 6. หนี้ / ข้อจำกัดที่ฝากไว้

1. **N1 น้อยเกินจริง (1.7% ควร 2–5%) และ N2 มากเกินไปเท่านั้น** — ตัวจำลองใส่ N1 แค่ตอนกำลังหลับ · 1 epoch ก่อนเข้า REM · 1–2 epoch หลังตื่นกลางคืน ของจริงมี N1 โปรยตามรอยต่ออื่นด้วย · **ไม่กระทบการตัดสินของ engine** เพราะ N1/N2 = light sleep ทั้งคู่และ Apple รวมเป็น `CORE` เหมือนกัน (ผลต่อ L2.5/L2.9 คือศูนย์) แต่ถ้าจะเอาไปวาด hypnogram ให้ผู้ใช้ดูควรแก้ก่อน
2. **ช่องว่าง `hrSd` REM(4–6) vs N3(~1) กว้างกว่าของจริง** — ผมตั้งจากค่ากลางของตำรา แต่ของจริงจากนาฬิกา (ไม่ใช่ ECG) จะมี noise การวัดบวกมาอีก ⇒ **F1 ที่ L2.5 ได้บนคืนจำลองจะดูดีกว่าคืนจริงแน่นอน** อย่าใช้เกณฑ์ F1 ≥ 0.6 จากคืนจำลองเป็นหลักฐานว่าใช้ได้จริง ต้องรอ fixture จาก R2 · ทางแก้เมื่อได้คืนจริง: ปรับ `HR_SD` / `HR_JITTER` ให้ตรงกับที่วัดได้ แล้วรัน oracle ซ้ำ
3. **ยังไม่มี fixture คืนจริง** — `replay.ts` ผ่านเฉพาะกับไฟล์ที่สร้างจากตัวจำลอง (ยังไม่มี diagnostics ของเจ้าของ) · เมื่อได้ไฟล์จาก R1 ควรวางไว้ `packages/engine/test/fixtures/` แล้วเพิ่มข้อสอบ replay จากไฟล์จริง
4. **`simulateNight` throw เมื่อ `durationMin < 120`** (ต่ำกว่านั้นรอบ 90 นาที + REM latency 60 นาทีอยู่ร่วมกันไม่ได้) — เป็นการ throw ที่ตั้งใจ ไม่ใช่ input ของผู้ใช้ปลายทาง
5. **`src/cli/sim.ts` ไม่ได้ export จาก `index.ts` โดยเจตนา** — มัน `import 'node:fs'` ถ้าดึงเข้า barrel แอปมือถือจะ bundle `node:fs` ไปด้วย · fitness กฎ A ไม่จับเรื่องนี้ (จับแค่ react-native/expo) ⇒ **ฝากเป็นกฎเพิ่มในอนาคต: ห้ามไฟล์ใน `packages/*` ที่ไม่ได้อยู่ใต้ `cli/` import `node:*`**
6. **`NightParams.mode = 'CONTROL'` ยังไม่มีใครใช้** — ประกาศไว้ให้ L2.6 · `resolveNightParams()` clamp volume เข้าราง 0.08–0.35 ไว้แล้วเพื่อให้ L2.6 ไม่ต้อง clamp เอง (ข้อสอบ L2.6 ข้อ "volume ไม่ออกนอกราง แม้ตั้งค่าพัง" จะผ่านได้ด้วยฟังก์ชันนี้)
7. **ตัวจำลองยังไม่มี "ตื่นเพราะเสียง"** — cue ยังไม่มีในใบนี้ ⇒ L2.6/L2.7 ต้องเพิ่ม hook (เช่น `simulateNight({ wakeAfterCueProb })`) หรือฉีดเหตุการณ์เข้าไปเองตอนทดสอบ วันนี้ผมไม่เดาสัญญาณไว้ล่วงหน้าเพราะยังไม่รู้ว่า L2.6 จะขอรูปแบบไหน

## 7. ข้อแย้ง (พร้อมหลักฐาน — ไม่ได้แก้ข้อสอบตามกติกา)

### ข้อแย้ง 1 (บล็อก `pnpm typecheck`) — ไฟล์ข้อสอบเองไม่ผ่าน `noUncheckedIndexedAccess`

`pnpm typecheck` = `tsc -b` ซึ่ง `packages/engine/tsconfig.json` include `test/**/*.ts` ด้วย ⇒ ไฟล์ข้อสอบถูก typecheck ไปพร้อมกัน และ error 2 บรรทัดนี้ **มาจากข้อสอบไม่ใช่โค้ดผม**:

```
$ pnpm typecheck        (unit lucid-typecheck-l21 · exit 2)
packages/engine/test/L2.1-simulate.test.ts(42,12): error TS18048: 'c.REM' is possibly 'undefined'.
packages/engine/test/L2.1-simulate.test.ts(42,57): error TS18048: 'c.REM' is possibly 'undefined'.
```

บรรทัด 39–42 ของข้อสอบ:
```ts
const c: Record<string, number> = {};
for (const s of n.truth) c[s.stage] = (c[s.stage] ?? 0) + 1;
const total = n.truth.length;
expect(c.REM / total).toBeGreaterThan(0.15); expect(c.REM / total).toBeLessThan(0.30);
```
`tsconfig.base.json` เปิด `noUncheckedIndexedAccess: true` ⇒ `c.REM` มีชนิด `number | undefined` · บรรทัดถัดไปที่เขียน `(c.WAKE ?? 0)` และ `(c.N3 ?? 0)` ผ่าน เพราะมี `??` — เฉพาะ `c.REM` 2 ที่ที่ลืมใส่

- **ไม่เกี่ยวกับโค้ดที่ผมเขียน** พิสูจน์แล้ว: สร้าง tsconfig ชั่วคราวที่ include `src/**/*.ts` + `test/diagnostics.test.ts` (ตัดไฟล์ข้อสอบออกอย่างเดียว) → `npx tsc -p tsconfig.l21check.json` **exit 0 ไม่มี error** (ลบ tsconfig ชั่วคราวแล้ว) · และ error นี้มีอยู่ตั้งแต่ก่อนผมเริ่ม (ตัวไฟล์ไม่เคย compile ผ่านเลยเพราะยังไม่มี `simulate.ts`)
- **ผมไม่แก้เอง** ตามคำสั่ง "ห้ามแก้ข้อสอบ" · เสนอให้ Fable แก้บรรทัด 42 เป็น `const remFrac = (c.REM ?? 0) / total;` แล้วใช้ `remFrac` สองที่ (หรือประกาศ `const c: Record<string, number> = { WAKE: 0, N1: 0, N2: 0, N3: 0, REM: 0 };`) — แก้แล้ว `pnpm typecheck` จะกลับมา exit 0 ทันที ไม่ต้องแตะโค้ด engine
- vitest ไม่ได้ typecheck (esbuild transpile ทิ้ง type) จึงรัน **ผ่าน 23/23** ได้ทั้งที่ `tsc` แดง

### ข้อแย้ง 2 (ไม่บล็อก) — สัญญา API ในหัวข้อสอบเขียน return ไม่ครบ

หัวไฟล์ข้อสอบเขียนว่า `simulateNight(...) → { epochs, truth, onsetT }` แต่คำสั่งงานให้คืน `{ epochs, truth, onsetT, params }` · ผมทำตามคำสั่งงาน (คืน `params` ด้วย) เพราะ E1 เทียบ `JSON.stringify` ทั้งก้อนจึงไม่ขัดกัน และ `params` จำเป็นกับ L2.5/L2.10 (ต้องรู้ว่าเฉลยรอบไหน/REM ก้อนไหน) — แจ้งไว้เผื่อ Fable ต้องการให้เอกสารสองที่ตรงกัน

### ข้อสังเกต 3 (ไม่ใช่ข้อแย้ง) — E7 นับ "ตื่นเช้า" เป็นหนึ่งช่วงด้วย

E7 นับทุก transition เข้า WAKE ที่ห่าง onset > 600 วิ ซึ่งรวม **WAKE ตอนเช้า** ที่คำสั่งงานสั่งให้มีปิดท้ายทุกคืน ⇒ `wakeCount = 3` จะนับได้ 4 ช่วง และผ่านได้ด้วยโควตา ±1 พอดี ผมจึงทำให้ **จำนวนช่วงตื่นกลางคืนเท่ากับ `wakeCount` เป๊ะเสมอ** (ไม่มากไม่น้อย) เพื่อไม่ให้ไปกินโควตา ±1 ที่เหลืออยู่ก้อนเดียว · ถ้าภายหลังอยากให้ `wakeCount` หมายถึง "รวมตื่นเช้า" ต้องแก้ทั้งข้อสอบและตัวจำลองพร้อมกัน

## 8. พร้อมให้ใบถัดไปใช้

- **L2.4 (onset)**: `params.latencyMin` + `onsetT` เป็นเฉลย · HR ในช่วง 5 นาทีแรกอยู่ระดับตื่น/N1 แล้วลดลง ~5–8% เมื่อเข้า N2/N3 ⇒ เกณฑ์ "HR ลด ≥ 8% + ขยับต่ำ 10 นาที" ทดสอบได้ทันที (หมายเหตุ: ค่ากลาง N2 = ฐานพอดี ⇒ ถ้า onset detector รอ −8% จากฐาน 5 นาทีแรก มันจะต้องรอถึง N3 ในหลายคืน — เผื่อไว้ว่า L2.4 อาจต้องขอให้ผมปรับ offset ของ N1/WAKE ช่วงต้นคืนให้สูงขึ้น ผมยังไม่แก้ล่วงหน้า)
- **L2.5 (REM estimator)**: `simulateNight` + `remMetrics` + `stageFractions` ครบ · ใช้ `engine:sim --nights 200 --out … --per-night` ทำ corpus ตายตัวแล้ว hold-out ด้วย seed ช่วงอื่น
- **L2.6/L2.7**: `NightParams` / `CueEvent` / `WakeEvent` / `resolveNightParams()` พร้อม · `params.wakeBouts` เป็นเฉลยของ "ตื่นจริง" ให้วัด false alarm ของตัวจับตื่น
- **L2.9**: `remMetrics` ตัวเดียวกันใช้กับเฉลย Apple ได้ (แปลง `AppleSleepPhase` → `StageSample` ต่อ epoch ก่อน)
