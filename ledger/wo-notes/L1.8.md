## 3. รายการตรวจ (จาก `scripts/qc-L1.8.spec.md`) — ข้อที่ข้อสอบไม่ได้จับ

### D16 — ห้ามเขียนไฟล์เสียงลง DB (path เท่านั้น)
หลักฐาน: ในสคีมาไม่มีคอลัมน์ BLOB เลยแม้แต่คอลัมน์เดียว

```
$ grep -niE "blob|audiodata|audiobytes|base64" packages/data/src/*.ts packages/data/src/drivers/*.ts
packages/data/src/schema.ts:11: *   - audio is a **path**, never a blob (oracle D16 · §0.5 S4).
$ grep -n "audioPath" packages/data/src/schema.ts
214:         "audioPath" TEXT,
```

- เสียงอยู่เป็น path ใน `MorningReport.audioPath` (TEXT) และ `UserProfile.anchorAudioPaths` (TEXT/JSON ต่อภาษา)
- `deleteAll()` **คืน `audioPaths: string[]`** ให้ผู้เรียก ไปลบไฟล์จริง (ทดสอบเองแล้ว: คืน `['/tmp/x.m4a']`) — ชั้นข้อมูลลบไฟล์เองไม่ได้เพราะแตะ filesystem ไม่ได้ (กฎ A) · การลบไฟล์/Keychain/`DELETE /device` ต่อที่ L3.6

### D20 — ห้าม SQL string concat ของค่าผู้ใช้
หลักฐาน: grep ทุก `${}` ในไฟล์ที่เขียน SQL แล้วไล่ดูทีละจุด

```
$ grep -nE '[$][{]' packages/data/src/repo.ts packages/data/src/schema.ts
repo.ts:1092  `SELECT * FROM "${table}" ORDER BY "rowid" ASC`      ← table ∈ TABLES (ค่าคงที่ในโค้ด)
repo.ts:1115  `DELETE FROM "${table}"`                             ← เหมือนกัน
repo.ts:1132  keys.map((key) => `"${key}"`)                        ← คอลัมน์ผ่าน whitelist จาก PRAGMA table_info
repo.ts:1135  `INSERT INTO "${table}" (${columnList}) VALUES (${placeholders})`  ← placeholders = '?' ล้วน
repo.ts:1149  `SELECT * FROM "${name}" ...`                        ← name ผ่าน assertTableName()
repo.ts:1179  `DELETE FROM "${table}"`                             ← table ∈ TABLES
schema.ts:80-89, 111-255   enumCheck()/boolCheck() ในคำสั่ง DDL   ← ค่า enum เป็น const ในไฟล์ ไม่มีทางมาจากผู้ใช้
schema.ts:277-290          "${META_TABLE}"                        ← ค่าคงที่
schema.ts:329  `PRAGMA table_info("${name}")`                      ← name ผ่าน assertTableName()
(repo.ts:416 คือการสร้าง id, repo.ts:540 คือการหนีอัญประกาศของ CSV — ไม่ใช่ SQL)
```

- **ค่าทุกค่าผูกด้วย `?` เท่านั้น** — ไม่มีจุดใดต่อค่าผู้ใช้เข้ากับสตริง SQL
- `importJson` ปฏิเสธคอลัมน์ที่ไม่มีในตาราง (`data: <table> has no column "<x>"`) ก่อนแตะ SQL จึงไม่มีทางเอาชื่อคอลัมน์จากไฟล์นำเข้าไปต่อสตริง
- ตัวตารางที่รับจากภายนอก (`exportCsv(table)`) ผ่าน `assertTableName` — ชื่อที่ไม่อยู่ใน 12 ชื่อ = โยน error

| D-F | ไม่มี migration ขาลง (down) | spec เขียน "migration ขึ้น/ลง idempotent" แต่ข้อสอบมีแต่ขาขึ้น · ผมทำ append-only + `IF NOT EXISTS` + กันเปิด DB ที่เวอร์ชันสูงกว่าโค้ด (โยน error) ซึ่งปลอดภัยกว่าการ downgrade ข้อมูลผู้ใช้ · ถ้า Fable ต้องการขาลงจริงต้องเพิ่มข้อสอบ |

## 5. ข้อแย้ง / จุดที่เอกสารกับข้อสอบไม่ตรงกัน (ไม่ได้แก้ข้อสอบ ตามกติกา)

1. **จำนวนตาราง 11 vs 12** — `APP-RUN.md` §2 "L1.8" เขียน *"สคีมา DESIGN §7 ครบ 11 ตาราง"* แต่ `DESIGN-APP.md` §7 มี **12** แถว (เพิ่ม `EarTest` ตอนมติ 24 ก.ย. ของ L1.6) และข้อสอบ D1 ระบุ 12 ชื่อ ⇒ ผมทำ **12** ตามข้อสอบ/DESIGN · เสนอให้ Fable แก้เลขใน APP-RUN §2 เป็น 12 (เอกสารเท่านั้น)
2. **ชื่อฟิลด์อ่อนไหว `aiSummary` vs `summary`** — `qc-L1.8.spec.md` D17 เขียน `(transcript audioPath aiSummary)` แต่ DESIGN §7 ตั้งคอลัมน์ของ `AiScore` ว่า `summary` และข้อสอบ D17 grep หา `'summary'` ⇒ ผมใส่ **ทั้งสองชื่อ** ใน `SENSITIVE_FIELDS` (`summary` = คอลัมน์จริง · `aiSummary` = ชื่อที่ฝั่งวิเคราะห์ใช้) ไม่ต้องแก้อะไร แค่ให้รู้ว่าไม่ได้พิมพ์ผิด
3. **`clock.now()` ในข้อสอบคืน `Date` ไม่ใช่ number** — บรรทัด 22 ของข้อสอบ: `{ now: () => new Date(...), nowIso: () => '...' }` ซึ่ง **ไม่ตรง** `Clock` ของ `@lucid/engine` (`now(): number`) · ทางแก้ที่ผมเลือก: repo ใช้ `nowIso()` เท่านั้น และรับ type `RepoClock = Pick<Clock,'nowIso'>` ⇒ ทั้ง `systemClock`/`fixedClock` ของ engine และ clock ในข้อสอบใช้ได้หมด ไม่มีการประกาศ type เวลาใหม่ · **ข้อควรระวังสำหรับข้อสอบใบหน้า**: ถ้าใบที่แตะเครื่องยนต์ (L2.x) ใช้ clock แบบเดียวกันนี้แล้วโค้ดเรียก `now()` จะได้ `Date` ไปทำเลขคณิต — ควรใช้ `fixedClock()` ของ engine ในข้อสอบพวกนั้น
4. **D11 ตรงกันได้เพราะ clock ถูกฉีด** — `exportJson().exportedAt` มาจาก clock ⇒ ในข้อสอบ repo กับ repo2 ใช้ clock เดียวกันจึงตรงกันจริง · บนเครื่องจริง (systemClock) export 2 ครั้งจะต่างกันที่ `exportedAt` ตามเจตนา ไม่ใช่บั๊ก
5. **D22 วัดเวลาจริง** — ผ่านแบบสบาย (33 ms จากเพดาน 2,000 ms) แต่เลขนี้เป็นของ **sql.js บน VPS** ไม่ใช่ของ expo-sqlite บน iPhone (ขอบเขตผลทดสอบ = การทดลองที่ทำ) · ของจริงต้องวัดในรอบ R1/R2 จาก diagnostics · ตัวช่วยที่เตรียมไว้: `sessions.appendEpochs()` ยัดทั้งชุดใน transaction เดียว ซึ่งเป็นทางที่นาฬิกาควรใช้ตอน flush
6. **`index` เป็นคำสงวนของ SQLite** — คอลัมน์ `CueEvent.index` (ตามสัญญาข้อสอบ `nightReport.cues[0].index`) ถูกใส่เครื่องหมายคำพูดทุกที่ `"index"` · ถ้าใครเขียน query ใหม่แบบไม่ quote จะพังทันที — เขียนไว้เตือน
7. **`stats(n)` นับเฉพาะคืนที่มี MorningReport** (ตามสเปก) และ `dateIso` เป็น "ป้ายคืนตามเวลาเครื่อง" ⇒ หน้าต่างเวลาจำกัดแต่ **ขอบล่าง** (`dateIso >= from`) ไม่ปิดขอบบน มิฉะนั้นผู้ใช้ทางตะวันออกของ UTC จะหายคืนล่าสุดไป 1 คืน (กับดัก `getDay()`/โซนเวลา)
8. **คืนที่ `lucid` เป็น null** นับเป็น "คืนที่มีรายงาน" (nights) แต่ให้ค่า 0 ในอัตราลูซิด — ข้อสอบไม่ได้ระบุ · ถ้า Fable ต้องการให้ข้ามคืนพวกนั้นออกจากตัวหาร บอกได้ แก้ 3 บรรทัด
